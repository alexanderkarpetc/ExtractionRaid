## Як вести трекер

- `⬜ queued` — ще не почато.
- `🔄 active` — є часткова реалізація або робота вже йде.
- `⛔ blocked` — потрібне зовнішнє рішення, асети чи інша задача.
- `✅ done` — критерії приймання виконані; деталі реалізації живуть у відповідному system doc.
- Оновлювати статус у тому самому коміті, що змінює реалізацію.
- Не дублювати task-таблиці, backlog або `next steps` в інших Markdown-файлах.

## Поточний фокус

**Найближча ціль — замкнений vertical slice, не весь v1.0.** Нижче — запропонована черга
роботи; її задачі ще не виконані. Межі повного релізу в `release-scope.md` не змінюються.

Гравець без dev cheats має пройти:

`бункер → спорядитися → рейд → бій/лут → ризикнути або вийти → extraction/KIA → бункер → поліпшення → нова ціль → наступний рейд`.

### Мінімальний обсяг slice

- Один бункер і одна наявна бойова мапа (`Test_Map`); за потреби обмежити тестовий маршрут,
  а не добудовувати всю мапу. Без другої мапи й нової художньої поліровки.
- Короткий безпечніший маршрут і необов'язкова небезпечніша зона з цінною здобиччю;
  робочий вихід, який можна знайти без допомоги розробника. Кілька виходів — лише якщо цього
  потребує маршрут; повний обсяг M1.3 не є автоматично обов'язковим для slice.
- 2–3 відчутно різні збірки з уже реалізованих cores; отримання частин у рейді,
  складання/модифікація в бункері й перевірка результату в наступному рейді.
- Короткий ланцюжок наявних квестів: перша вилазка → корисна знахідка → Builder/апгрейд →
  наступна конкретна ціль. Не створювати нову кампанію поверх чинної.
- Невеликий набір справді працюючих progression-вузлів і мінімальне поповнення боєприпасів/
  лікування. Решта дерева та бункерних систем не повинна обіцяти недоступний результат.

### Що показав аудит

Основа вже існує: deploy/return у [App](../../Assets/Scripts/ApplicationCore/App.cs),
extraction і таймер, gear loss і стартовий комплект, loot/stash/shop/craft/quests,
Builder та матеріальна progression. Це робота над надійністю й зв'язками, не створення всього з нуля.

Конкретні ризики з коду, для яких потрібні виправлення й regression-перевірки:

- **Втрата встановлених attachments після завантаження.**
  [WeaponConfiguration](../../Assets/Scripts/State/WeaponConfiguration.cs) має `Attachments`,
  але [WeaponConfigSaveData](../../Assets/Scripts/Save/SaveData.cs) їх не записує й не відновлює → VS02.
- **Обхід extraction через звичайний вихід.**
  [AppBootstrap](../../Assets/Scripts/ApplicationCore/AppBootstrap.cs) викликає shutdown при виході
  в меню/закритті; [App.EndRaid](../../Assets/Scripts/ApplicationCore/App.cs) очищає спорядження
  лише при KIA. Незавершений бойовий рейд з outcome `None` зберігає інвентар. Це шлях у коді,
  а не вже відтворений UI-тест → VS01.
- **Результат extraction залежить від UI.**
  [ExtractionHudPresenter](../../Assets/Scripts/View/ExtractionHudPresenter.cs) викликає
  `RequestExtraction` лише після знаходження вікна. Завершення рейду має визначатися поза HUD → VS01.
- **Save без захисту попереднього запису.**
  [SaveManager](../../Assets/Scripts/Save/SaveManager.cs) прямо перезаписує файл; помилка лише
  логується, невдале читання повертає `null`. Немає атомарної заміни/резервної копії → VS02.
- **Можна оплатити вузол без підключеного gameplay-ефекту.**
  [ProgressionCostSystem](../../Assets/Scripts/Systems/ProgressionCostSystem.cs) перевіряє зв'язність
  і вартість, але не runtime-підтримку; частина ефектів лишається data-only за
  [progression contract](./progression.md). Конкретний набір доступних у сцені вузлів ще
  потрібно перевірити в Editor → VS10.

Наявні [GearLossTests](../../Assets/Tests/EditMode/GearLossTests.cs) перевіряють очищення й gate
стартового комплекту, а [WeaponBuilderEndToEndTests](../../Assets/Tests/EditMode/WeaponBuilderEndToEndTests.cs)
— Builder → runtime weapon. Вони не доводять проходження всього циклу зі сценами й save/load.
Повного автоматизованого outcome/save/quest потоку під час аудиту не знайдено.

### Критерії приймання VS-задач

**VS00 — контрольний маршрут.** У Unity/standalone пройти новий профіль від головного меню,
зафіксувати де зупиняється цикл: сцена/місце, дії, очікуване й фактичне, відео або лог.
Вибрати старт, основну й ризикову зони, вихід, квести та збірки для наступних перевірок.
Зафіксувати тестовий build, цільове залізо й прийнятний FPS/frame-time. Вимкнути cheats,
автовидалення save та тестові grants; не видаляти основний профіль тестувальника.

**VS01 — результат рейду.** Session/App фіксує завершення рівно один раз; HUD тільки показує
результат. Extraction зберігає принесене, KIA/timeout забирає carried gear, stash і постійні
апгрейди лишаються. Окремо узгодити й реалізувати правило abandon/crash: рекомендовано
abandon = втрата carried gear, без можливості винести новий лут закриттям гри. Збереження
в бункері не є abandon. Закрити тести на повторний запит, смерть/таймер на межі extraction,
вихід у меню/на desktop, перезапуск після аварійного закриття та повернення без завислого input.
Правило crash не означає, що для slice потрібно реалізовувати mid-raid resume.

**VS02 — persistence.** Round-trip через JSON і новий процес зберігає cores/rarity/attachments,
магазин і запас ammo, durability, залишок ресурсу аптечки, backpack/quick slots/stash,
квести, credits, будівлі та відкриті вузли. Зробити контрольований запис із захистом останнього
валідного save й видимою помилкою; пошкоджений файл не перетворюється мовчки на новий профіль.
Визначити save checkpoints для outcome та завершених бункерних транзакцій. Мінімальна schema
version і сумісність із поточним тестовим save; не будувати універсальну систему міграцій.
Відмова запису/повтор дії не дублює й не списує повторно нагороду або вартість.

**VS03 — combat readability.** Закрити PT16. На відкритій місцевості, впритул і біля укриття
приціл, напрямок пострілу та результат узгоджені; зрозуміло, чи влучив гравець, у що саме,
чому не може стріляти та коли завершиться reload. Перевірити swap/reload/empty magazine,
лікування, броню й смерть на обраних збірках. Додавати лише потрібні для цього SFX/VFX,
а не весь M2.1/M2.4. Focused tests плюс ручна перевірка відчуття бою.

**VS04 — надійний AI.** Відтворити PT5/PT7/PT10 на маршруті, відокремити логіку від NavMesh,
колізій і spawn authoring. Бот не веде безкінечний вогонь у стіну, виходить зі stuck-стану,
не створює нечитабельний позаекранний lethal focus; пошук після втрати контакту передбачуваний.
Початок рейду дозволяє зорієнтуватися, зона ключа/складу проходиться штатним спорядженням.
Достатньо чинних типів ворогів: без нового AI-фреймворку, фракцій чи симуляції життя ботів.

**VS05 — спорядження й recovery.** Новий гравець знаходить перший квест (він зараз відкриває
deploy), stash і вихід із бункера; переносить, одягає та бере потрібні ammo/ліки без втрат
або дублів. Мінімальні buy/sell дії показують ціну, кількість і результат. Після повторних
смертей є досяжний спосіб знову вийти з придатною зброєю; перевірити також стан «є матеріали,
але немає зброї/ammo», який не проходить нинішній `IsInventoryEmpty` gate. Спорожнення backpack
у stash й повторний deploy не повинні давати необмежений прибуток зі стартових grants.

**VS06 — extraction UX.** Без підказки розробника можна знайти доступний вихід, розпізнати
межу зони, прогрес, скасування при виході й успіх. Перевірити досяжність у сцені, повторний
вхід, край таймера, ворогів біля виходу й наступний рейд. Відсутній/прихований HUD не блокує
сам outcome. Мінімальні маркери й текст достатні; фінальний visual pass не потрібен.

**VS07 — ризик і цінність.** Кожна обрана збірка/апгрейд має доступне джерело потрібних
матеріалів/частин; PT19 перевірений реальними рейдами, а не лише середнім drop rate.
Стартові нагороди не знецінюють лікування/пошук (PT1). Ризикова зона дає зрозумілу додаткову
цінність, але не є обов'язковою пасткою першого рейду. Тестувальник може пояснити, що вже
ризикує втратити, навіщо йти далі та на що витратить знахідку. Після визначення витрат
VS08–VS10 звести supply/demand на одній мапі; не балансувати весь каталог релізу.

**VS08 — Builder як головна фіча.** Гравець сам відкриває/будує потрібну станцію, розуміє
`have/need`, приносить частини, складає й екіпірує зброю. Якщо Builder бере лише з backpack,
це явно пояснено або шлях зі stash спрощено. 2–3 обрані збірки відрізняються поведінкою й
тактичним застосуванням, а не лише цифрою damage; preview відповідає бою. Перевірити оплату,
невдалу/повторну збірку, повний інвентар, install/remove attachment, доступність ammo й
збереження результату. Виносити правила з presenter у System локально там, де це потрібно
для надійної транзакції/тестів; не робити загальну перебудову архітектури.

**VS09 — коротка quest arc.** Використати чинний початок: зрозумілі місце ключа, актуальний
NPC marker, умови здачі, вимоги Builder, спосіб зібрати потрібну зброю. Нагорода видається
рівно один раз; перевірити повний backpack, часткову здачу, смерть із квестовим предметом,
знахідку до прийняття квесту й restart. Після поліпшення є наступна досяжна ціль з причиною
знову йти в рейд. Критерій — самостійне проходження, не красиве quest window.

**VS10 — мінімальна progression.** Вибрати невеликий зв'язний набір уже підключених ефектів,
який реально купити в межах тестового циклу. Непрацюючі вузли поза slice недоступні для
оплати й позначені відповідно; блокування перевіряється не лише UI. Купівля списує вартість
один раз, результат впливає на наступний рейд і переживає смерть/restart. Для кожного
доступного ефекту є перевірка зміни gameplay. Повні Warden/Phantom/Prospector не є gate.

**VS11 — приймання.** Focused EditMode tests для змінених систем і meta-транзакцій плюс
повний доступний EditMode suite; записати фактичний результат запуску. У standalone виконати
сценарії нижче й короткий perf pass на залізі VS00. Запропонований фінальний gate: три нові
тестувальники проходять цикл без усних інструкцій; кожен доходить до поліпшення та наступного
рейду, розуміє втрати й називає свою наступну ціль. Не вимагати, щоб вони вижили в кожній
спробі. Нуль відомих втрат/дублів save-даних і блокерів маршруту; косметика не блокує приймання.

### Контрольний сценарій приймання

1. Новий тестовий профіль → прийняти стартову ціль → обрати спорядження → звичайний deploy.
2. Бій, лікування, лут і потрібна частина → рішення вийти → extraction → перевірка принесеного.
3. Stash/потрібна транзакція → Builder або attachment → доступний progression-апгрейд →
   наступна ціль → закрити гру й Continue; спорядження та прогрес збігаються.
4. Наступний рейд новою зброєю → смерть із лутом → carried gear втрачено, stash/постійні
   поліпшення збережено → спорядитися й знову зайти без dev grants.
5. Ще один успішний рейд: зміни зброї відчутні, нова ціль просувається, повернення працює.
6. Окремі regression-сценарії: timeout; abandon; crash/restart; full backpack; повторна здача
   квесту/натискання Build/Next; пошкоджений save/відмова запису. Не відтворювати руйнівні
   перевірки на основному профілі. Фіксувати очікуваний і фактичний стан до/після.

### Що не беремо до завершення slice

Друга мапа (M3.1), нові cores/exotics (M2.2/M2.3), повне дерево progression (решта M2.7),
фінальний bunker/environment art, нові пропси, повний audio/music/settings pass,
всі іконки й красиві меню. Не починати A1–A4 як окремий великий refactor, якщо конкретний
дефект не блокує VS-задачу; нові правки все одно мають дотримуватися архітектурного контракту.
Світло/іконка/звук стають пріоритетом тільки коли без них не читається бій, предмет або вихід.

Починати з **VS00 → VS01/VS02**, потім закрити бойові й маршрутні P0. Потреби Builder,
квестів і progression визначити разом, після цього балансувати їхній loot supply в VS07.
Не чекати завершення всього release backlog, щоб передати slice тестувальникам.
